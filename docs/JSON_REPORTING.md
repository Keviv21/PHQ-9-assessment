# Reports from local assessment JSON

Reports are generated locally from the saved assessment definition and saved patient responses. No reference website, report PDF, image URL, external font, or LLM is consulted. Bibliographic citations are rendered as plain text without URLs. PDF rendering blocks every network request.

## Use

Open **Analytics**, select a patient, an assessment, and a completed visit. The visit panel embeds the same report preview used by **Open report**. Choose **Download PDF** to download a real PDF, or **Print / Save as PDF** to use browser printing. HTML downloads remain supported.

The server uses local Chromium through pinned `playwright-core`. On a new host run `npm run reports:install-browser` during setup, or set `REPORT_CHROMIUM_PATH` to an installed compatible Chromium executable. This browser installation is a software dependency; no assessment/report reference content is downloaded. PDF requests return a clear 503 when the renderer is missing or busy; they never silently return HTML as a PDF. Rendering uses a fresh browser, disables JavaScript, blocks service workers/network requests, and allows at most two concurrent jobs. Reports are returned with `Cache-Control: no-store` and are not written to disk by the server.

## Data and calculations

`data/assessments/catalogue.json` is generated by `scripts/assessments/import-catalogue.mjs` from the local `all-assessments.json` clean export. The importer retains the original questionnaire/response sets, administration, scoring rules, report configuration, rights, references, review information and technical verification evidence alongside the application's normalized questions. Source SHA-256 is recorded. It does not load linked documents or execute extracted prose.

`report-calculation.js` supports the bundle's sum, mean, threshold-count and weighted-sum methods. It uses explicit numeric encodings, coefficients, transforms, option overrides, optional items, eligibility/context and missing policies. Printed reverse encodings are applied once; a descriptive reverse flag never causes an additional reversal. Unsupported rules, missing required responses/context, and invalid results are withheld. No option-position scoring, imputation, percentile conversion or inferred diagnosis is used.

`assessmentReport()` constructs the shared result object. HTML, embedded analytics, JSON and PDF use that object. Charts use each metric's own range. Compatible history is restricted by patient, assessment, definition/scoring/reporting snapshot, language, respondent and context; only completed visits up to the selected visit are included. Baseline/previous comparisons are deduplicated and use neutral numeric change. Unavailable values remain gaps. Configured response groups, individual response histories, item charts, source citations and limitations are retained.

Existing sessions keep their saved definition snapshots. Reports do not silently attach new catalogue rules to older administrations. The retained historical WSAS administration therefore remains a response report if its snapshot did not contain detailed rules. The JSON API is `GET /api/workspace/sessions/:id/report?format=json`; PDF uses `?format=pdf`. Both resolve patient identity from the saved session and use the existing workspace access boundary. This change does not add login or patient-access controls.

## Development previews

Clinical interpretation still honors scoring and review gates. All 186 supplied definitions have clinical scoring disabled. Draft numeric scoring is enabled when a patient submits an assessment. The application stores `calculatedResults` with the completed session (PostgreSQL: `assessments.assessment_sessions.data.calculatedResults`; SQLite: `workspace_sessions.data`). It records metric values, ranges, status, calculation time/version, definition version and an input hash. Completion screens, reports, PDF and patient assessment trends use these saved results. Each draft score is labelled **Draft score — not clinically validated**; clinical approval flags stay unchanged and draft severity descriptors are withheld. Missing or unsupported rules still produce unavailable results. Screening interpretation stays gated. Existing completed assessments are not automatically rescored.

The developer CLI also generates synthetic answers itself and never reads the patient database:

```sh
npm run reports:validate
npm run reports:preview -- brief-addiction-monitor-bam--dce6e8665d04 /tmp/bam-preview.html
```

Run `npm run reports:preview` without arguments to list exact assessment IDs. Choose an `.html` or `.pdf` output path. Every preview is labelled **DEVELOPMENT PREVIEW — SYNTHETIC DATA** with a fixed synthetic date. Report requests do not enable draft scoring or recalculate old results. Patient reports still reject the synthetic-preview option for real sessions.

## Clinical and feature limits

- All 186 records await independent clinical validation. Configuration tests do not establish clinical validity. The 45 records with explicit remaining work are listed in `REPORTING_COVERAGE.md`.
- BAM preserves Substance Use 0–90, Risk Factors 0–180 and Protective Factors 0–180, and configured item charts. It never creates an overall total.
- CRAFFT retains core responses, nicotine follow-up and substance-use frequencies separately. The supplied JSON does not provide a complete verified executable risk-classification algorithm; the report does not invent categories, flags or personal probabilities.
- LEC-5 remains descriptive. asQ has categorical draft states in synthetic previews; real screening interpretation remains gated and no numeric total is created.
- SDQ remains unavailable. WHODAS context-dependent forms remain unavailable for administration where the existing questionnaire UI cannot capture required context. ORT results require explicit source-scoring context; demographic gender is not substituted for it.
- MAPsy exposes only the configured Harmful Substance Use draft arithmetic and explicitly states its partial coverage.
- Paired-assessment profiles are preserved but withheld: selection/verification of a compatible paired administration is not implemented. Source interpretation prose remains reference data and is not executed or presented as patient-specific guidance.
- Unknown score directions are neutral. No normative percentiles, reliable-change thresholds, diagnoses or treatment recommendations are generated.
- Historical sessions without the new reporting configuration show their saved responses and explicitly recorded legacy results, if any; no retrospective scoring upgrade occurs.
- Clinical enablement requires independent validation and a reviewed application change. The importer intentionally keeps imported scoring disabled.

## Validation

`npm run reports:validate` checks all 186 report modes, 729 rule/metric bindings, item membership, response groups and item histories. `node --test` includes arithmetic, missing/branch/context handling, unsupported rules, synthetic gates, compatibility, patient isolation, and local PDF API tests. PDF tests require local Chromium; PostgreSQL tests retain their existing separate test-database requirement.
